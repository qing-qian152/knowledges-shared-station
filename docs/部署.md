# 部署与运维

站点是静态托管，没有服务器要维护。真正会咬人的只有三件事：**Pages 的来源设置**、
**Service Worker 的版本号**、**内容断更没人发现**。

---

## 首次部署（GitHub Pages）

1. 仓库 **Settings → Pages**：`Source` 选 **Deploy from a branch**，分支 `main`，目录 **`/ (root)`**。
   → 所以**根目录就是网站根**，别把 `index.html` 挪进子目录（原因见 [架构.md](架构.md#为什么不把站点塞进子目录)）。
2. 确认根目录有 `.nojekyll`。没有它 Pages 会走 Jekyll 处理，某些以 `_` 开头的路径会被吞掉。
   注意：它必须放在**仓库根目录**，放在 `.github/workflows/` 里是无效的。
3. 一两分钟后访问 `https://<用户名>.github.io/<仓库名>/`。
4. 想用自定义域名：根目录加 `CNAME` 文件写入域名，DNS 里加 CNAME 指向 `<用户名>.github.io`。

时间账本（`time-ledger/`）没有单独的部署：它跟站点同一个仓库，直接访问
`https://<用户名>.github.io/<仓库名>/time-ledger/` 即可，或本地双击 `time-ledger/index.html`。

## 只有一个 workflow

| 文件 | 干什么 | 触发 |
| --- | --- | --- |
| `.github/workflows/verify.yml` | 只检查不写文件：语法 → 结构体检 → 主题体检 → 内容全量校验 → 生成物是否过期 | 每次 push / PR / 手动 |

仓库里**没有**「自动生成内容」的 workflow。早期有一个（定时调模型 API 生成并提交），
2026-11-22 连同脚本、主题池与相关 Secret 一起删除了，原因见 [AGENTS.md](../AGENTS.md#只有一种更新方式)。

### verify.yml

五个步骤对应本地这四条命令（外加 JS / Python 语法检查）：

```bash
node scripts/check-structure.mjs
node scripts/check-themes.mjs
python scripts/daytool.py check --all
python scripts/daytool.py site && git diff --exit-code
```

最后一步是重点：`sitemap.xml` / `robots.txt` / `data/days/index.js` / `index.html` 的归档区
都是脚本产物，忘了 `publish` 就会落后于 `data/`。CI 重跑一次再比 diff，不同步就红。

## 每天 06:30 的自动发布

现在的日常产出**不经过任何模型接口**：由 **WorkBuddy 的定时任务**在北京时间 06:30
拉起一次 agent 会话，按 [AGENTS.md](../AGENTS.md) 的流程写内容并发布：

```
检查是否已存在 → 选题 → daytool new → 分板块写 5 个 JSON
→ build（校验）→ publish --git（重建索引 + 推送）→ 跑四条体检 → 自查线上 200
```

几点设计上的考虑：

- **不覆盖已有内容**：当天文件已存在就直接跳过，只做补推。所以手动先写一天也不会被冲掉。
- **不合格不发**：`build` / `publish` 自带校验，语文不足 1000 字、译文段数不符、诗词与近 4 期重复等都会拒绝写入。
- **推送会重试**：`daytool.py` 的 `git_push()` 把「直连 / 本机网关 / git 自身配置」三条路径各试 3 轮，
  失败时内容已经提交在本地，**下一次 publish 会把积压的提交一起推上去**，不会丢。
- **断了一天不影响第二天**：`publish` 用的是 `git push origin HEAD:main`，积压的提交一次推完。

出问题时的判断顺序：

| 现象 | 先看 |
| --- | --- |
| 早上打开还是昨天 | 当天文件是否存在于 `data/days/`；定时任务是否真的跑了 |
| 有文件但线上 404 | Pages 是否重建（约 20 秒）；`git log` 里有没有这条提交被推上去 |
| 本地有提交、远端没有 | 网络问题，重跑 `python scripts/daytool.py publish --git` 或手动 `git push` |
| 内容质量不合格 | 看 CI 的 `check --all` 报了什么，按 [内容规范.md](内容规范.md) 改 |

## 时区

站点上「今天是哪天」按 `TZ=Asia/Shanghai` 计算（`daytool.py` 里固定 `+08:00`）。
这条规则以前由 workflow 的 `TZ` 变量保证，现在由脚本自己保证，**换机器也不会差一天**。
GitHub Actions 的 Runner 是 UTC，`verify.yml` 因此不依赖开头的日期判断，只做校验。

## 发完之后自查

```bash
# 当天文件是否已上线（Pages 重建约 20 秒，CDN 完全生效可能要 10 分钟）
curl -s -o /dev/null -w "%{http_code}\n" \
  https://qing-qian152.github.io/knowledges-shared-station/data/days/2026-11-23.js
```

再打开 `https://qing-qian152.github.io/knowledges-shared-station/?d=2026-11-23`，
确认四个板块都渲染出来、日期下拉里能看到这一天。

## 缓存：改了外壳必须改版本号

| 改了什么 | 要不要改 `sw.js` 的 `VERSION` |
| --- | --- |
| `assets/*`、`index.html` 骨架、`manifest.json`、`sw.js` 自身 | **要**（现在是 `v12`） |
| `data/days/*.js`（每日内容） | 不用，内容走网络优先 |

不改版本号的后果：老访客永远拿旧外壳，而且不会有任何报错提示——
表现是"我明明改了样式，别人却说没变"。

## 断更了怎么补

`data/days/` 里缺哪天，就按那天补一篇（选题避开前后各 5 期已用的主题与诗词）：

```bash
python scripts/daytool.py new     --date 2026-11-16
python scripts/daytool.py build   --date 2026-11-16
python scripts/daytool.py publish --date 2026-11-16
```

补完后 `publish` 会重建索引与 sitemap，往期链接自动出现。
如果只想重建站点产物（不动内容），用：

```bash
python scripts/daytool.py site
```

## 常见问题

**页面打不开 / 打开是旧内容**
先确认 `sw.js` 版本号是否改过；再在浏览器 DevTools → Application → Service Workers 里
Unregister，然后硬刷新。

**`?d=2026-11-23` 是 404**
说明当天文件没上线。看 `verify.yml` 是否红、Pages 是否已重建。

**日期下拉里没有今天**
`data/days/index.js` 没更新——跑 `python scripts/daytool.py site` 并提交。

**样式改了别人看不到**
`VERSION` 没加一。

**CI 红在「生成物是否过期」**
本地跑 `python scripts/daytool.py site`，把产生的 diff 一起提交。
